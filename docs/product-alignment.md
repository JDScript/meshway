# 产品对齐记录

本页记录 2026-10-01 起主线程逐项确认的产品要求。实现状态以各功能文档与实际验收为准。

## 已确认

- **平台托管配置**：Agent 完成首次接入后，V2Ray / Shadowsocks 等协议配置、凭据、监听和后续变更均由平台管理、下发，日常使用在 Web 完成。手工复制配置、维护本地 profiles 或反复 SSH 调参不属于目标使用流程。
- **协议服务对象**（问题 1 已确认）：这些协议用于 Meshway 内部传输承载；后续终端设备通过 Meshway App 接入。普通 Clash / sing-box / V2Ray 客户端直连代理入口，以及相应账户 / 订阅服务，不属于当前产品目标。
- **默认按需建连**（问题 2 已确认）：平台根据访问授权、路径规则和可达性自动组织节点连接，并允许通过 Web 手动指定或限制。用户无需先配置每对节点关系；自动建连不改变 Access 授权或绕过明确的必经节点。这是目标行为，当前手工连接实现仍待收敛。
- **统一节点模型**（问题 3 收敛）：不按服务器 Agent / App 预设不同节点类别或中继资格。路径经过谁，谁承担相应中转职责；平台依据实际能力、可达性与授权进行选择，不额外增加用户需要维护的节点角色开关。运行环境差异由底层能力模型处理。
- **首版双核心闭环**（问题 4 已确认，选择 C）：Mesh 私网互访和终端按域名 / IP 经指定路径访问互联网同为首版核心。公网出口、域名分流应与平台配置下发、自动建连一起形成可用流程，不继续仅按旧技术路线推迟到后期。
- **承载默认自动、保留 listener 控制**（问题 5 已确认）：平台提供默认协议优先级、自动选择 / 主备切换，并生成和下发默认参数、凭据；Web 可限制允许协议、调整优先级和覆盖某段承载。添加节点时提供可选 listener 配置入口，后续可在节点页修改；不要求用户逐对配置拨号候选。
- **多网络隔离**（问题 6 已确认，选择 B）：一个 controller 托管多张独立网络，采用类似 tailnet 的边界。每张网络拥有独立成员、地址、DNS、Access、路由及相关配置，网络之间默认隔离；Web 选择网络后在该范围内操作。节点保持统一模型，现有有序路径与授权语义不因参考 Tailscale 而改变。
- **一台设备一张网络**（问题 7 已确认，选择 A）：设备可保存多个网络接入并切换，同一时间只接入一张，不在多网同时传输。与 [Tailscale fast user switching](https://tailscale.com/docs/features/client/fast-user-switching) 一致。
- **以 Tailscale 为产品基线**：常规场景贴近 Tailscale。Meshway 的差异只有两项扩展：可插拔的自定义 transport 承载（平台托管、自动选择与主备），以及按域名 / IP 经有序指定路径的 routing（多跳链路、指定出口）。网络、设备与用户、接入、授权、DNS、出口、控制台和客户端等定义默认参照 Tailscale 官方做法；只有上述扩展需要时才偏离，并说明理由。
- **Access 改为叠加授权**（问题 8 已确认，选择 A）：参照 Tailscale grants，只写允许规则，未匹配即拒绝，多条规则取并集、与顺序无关；新网络默认模板为成员之间全部允许。原有序 first-match allow/reject 语义废止，现有“默认允许、0 条规则”无损迁移为一条全部允许规则。
- **用户身份与链接登录**：参照 Tailscale，设备归属登录它的用户，服务器类设备可使用预分配 tag 的接入密钥；授权可按用户 / 组书写。Agent 提供类似 `tailscale up` 的链接登录（终端打印链接，浏览器完成登录），Apple App 使用已确认的系统浏览器 SSO。
- **本地账户先行**（问题 10 已确认，选择 B）：首版由 controller 自己管理账户，用户以邮箱 + 密码注册和登录，密码只存安全哈希。OIDC 等外部身份提供方后续再接入，不阻塞首版。角色划分默认参照 Tailscale。
- **仅邀请加入**（问题 11 已确认，选择 B）：不开放自助注册。管理员或网络 Owner 生成邀请链接，对方用邮箱 + 密码注册后加入指定网络；现有管理员迁移为第一个 Owner。首版不发邮件，邀请与重置密码链接在 Web 生成后手动转交。
- **Access 与 Routing 分开**：授权回答“能不能访问”，路由回答“走哪条路”，保持两套独立策略，不合并为 grant 的 `via` 字段。
- **前端整体整理并行推进**：内部诊断字段收进高级详情，页面围绕用户任务组织；正常状态和失败原因仍需真实可见。
- **统一开发入口**：收拢 Controller、Web dev、文档和 Docker demo 的启动、状态检查与更新入口，保持现有身份、业务配置和可写开发容器中的工具。
- **性能专项并行推进**：用户观察到 Docker 原生网络约 100 Gbps、隧道约 300 Mbps，中转后更低。首先复现并定位瓶颈，再报告匹配条件下的改进。这个反馈不是本项目已复测的性能结论。
- **逐题对齐**：主线程每次只讨论一个产品问题；后台优化不替代产品决策。

### 四层策略模型（问题 9 已确认）

各层均与规则顺序无关：

1. **连接**（Meshway 扩展，决定哪些节点之间可以直接建立承载连接）
   - 有 listener 的节点可被拨入；没有 listener 的节点（如手机）只主动拨出。建连方向不影响业务方向。
   - 默认模板允许所有节点在可达时直连；可用 node / tag 规则阻断某些直连。允许规则取并集，阻断规则始终优先。删除默认的“全部允许”即变为默认不连，再逐条允许需要的连接。
   - 实际连接只在已授权流量需要经过时按需建立，不预先全连。直连被阻断或不可达时，平台经允许的连接自动中转，并保持 E2E 加密。
2. **授权**：问题 8 已确认的叠加 grants。
3. **Mesh 内路由**（可选）：要求某些 Mesh 内流量必须依次经过指定节点；没有规则时由平台自动选路。越具体的规则越优先（node > tag > 全部）；同一具体程度的规则冲突时，保存即报错，不靠顺序。
4. **出口路由**：域名后缀 / IP 段 → 出口节点（可多个候选，主备切换），可指定出口前的中转节点。与 IP 路由表一样，最长前缀 / 最长域名后缀优先，与顺序无关。未匹配的流量不接管、走设备本地网络；可设置默认出口，让全部流量经出口。使用出口需要授权允许访问互联网（参照 Tailscale `autogroup:internet`）。

原 routing 的有序 first-match 与初始空策略 reject 由此废止。现有策略须无损迁移；无法等价转换的部分必须明确报告，不能静默改变行为。

### 与 Tailscale 基线不一致、待逐项复核

以下是早先确认或已实现、但与 Tailscale 做法不同的地方。每项单独确认，确认前保持现状：

- 互联网出口由管理员规则集中决定；Tailscale 由设备自行选择已获批准的 exit node，管理员通过 grants 与 `via` 限制可用范围。
- 出口节点是否需要设备所有者同意 / 管理员批准；Tailscale 要求设备通告并经管理员批准。
- 手工“连接”页面与节点本地 profiles；Tailscale 中设备自动互联，无连接配置。自动建连与平台托管已确认，待实现。

## 当前实现与目标的差距

目前 VLESS 的部分凭据和证书仍从节点本地 profiles 加载；Shadowsocks 等已有库级适配，未完成统一的平台配置分发。这些是当前实现边界，需要向上述托管目标收敛，不能把目标描述为已经完成。

控制面当前仍使用单网络存储和作用域；多网络需要真实的数据、权限与数据面隔离以及既有身份 / 地址的无损迁移，不是增加一个切换菜单就完成。

## Tailnet 对照依据

- [What is a tailnet?](https://tailscale.com/docs/concepts/tailnet)：用户、设备、资源、DNS 与访问策略的网络边界。
- [Fast user switching](https://tailscale.com/docs/features/client/fast-user-switching)：同一客户端保存多个账户，一次只有一个活动账户，不同时在多张 tailnet 传输。Meshway 已按问题 7 采用。
- [Grants](https://tailscale.com/kb/1324/grants)、[Route filtering with Via](https://tailscale.com/docs/features/access-control/grants/grants-via)：只允许、默认拒绝；`via` 仅以 tag 限定可用的 exit node / subnet router / app connector，不是有序 hop 序列。
- [Exit nodes](https://tailscale.com/kb/1103/exit-nodes)、[App connectors](https://tailscale.com/kb/1281/app-connectors)：设备通告、管理员批准、`autogroup:internet` 授权、终端自行选用；app connector 按域名经指定设备访问应用。
