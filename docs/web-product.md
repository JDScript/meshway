# Web 产品与交互

Web 的产品方向是团队化网络管理：在明确的团队 / 网络上下文中，查看节点与运行情况、理解路径、配置策略并确认下发结果。当前以单 controller 的真实能力为基础推进界面，后续接入团队、传输测量及实际转发数据。

## 页面与工作流

| 页面 | 当前能力 |
| --- | --- |
| `/` | 真实节点、近期控制面联系、配置确认覆盖、策略摘要与待处理事项 |
| `/nodes` | 搜索、状态 / 配置筛选、排序，进入独立节点详情，国家标注及撤销 |
| `/nodes/[id]` | 概览与连接页：身份、控制面联系、独立保存回执、实际应用与认证邻接、按节点编辑配置 |
| `/connections` | 全网节点连接概览、主动拨号关系与监听入口；按任务添加，机器 ID / 优先级放在高级设置 |
| `/routing` | 有序规则列表、规则编辑 Sheet、草稿预览、条件保存及冲突处理 |
| `/topology` | 节点逻辑布局、controller 编译的规划路径、节点详情与路径文字版 |
| `/monitoring` | 诊断工作台：已保存 Flow、邻接 / 身份、DNS、独立 netcheck 与实际 UDP carrier 候选观测；保留原 URL 与真实联系时间分布 |
| `/enrollment` | 创建一次性注册令牌、生成可复制的注册与运行命令 |

侧栏按网络和运维组织；移动端使用 Sheet。顶部提供当前上下文、搜索 / 跳转与能力说明，账户菜单管理外观和登出。明暗主题共用语义颜色体系。

## 当前上下文与未来团队

当前 API 提供一个 controller 下的节点、地址池、策略和配置版本，还没有 Team、成员关系或多个 Network 资源。界面中的上下文入口应标识真实的当前控制器 / 网络；新增团队及切换团队需要后续的身份、资源归属和授权 API。

团队化后，导航、搜索、草稿、配置版本和待完成操作都需要绑定明确的网络上下文。切换上下文时，应处理未保存草稿和尚未完成的请求，不能只替换页面标题而沿用另一个网络的数据或保存基准。

## Dashboard 与监控数据

| 信息 | 当前数据依据 | 呈现含义 |
| --- | --- | --- |
| 注册 / 撤销节点 | `NodeSummary.revoked_at` | 控制面凭据状态 |
| 最近联系 | `NodeSummary.last_seen` | 最近联系 controller 的时间；统计须标明时间窗口 |
| 配置确认覆盖 | `configuration_revision` 与 `acknowledged_revision` | Agent 对当前配置的校验、保存与回执进度 |
| 路由概览 | `PolicySnapshot` | 默认动作、规则数量、源策略有效性与版本 |
| 网络地址 | `MeshNetwork`、节点 mesh 地址 | 已分配的地址空间与节点地址 |

节点间 RTT、丢包、带宽、流量历史与实际选用的 transport 尚需数据面接口。监控视图应区分“尚未测量”、真实零值和测量过期；控制面 HTTP 响应或心跳时间不能代替节点间延迟。

## 路由地图

当前地图可使用真实节点清单和编译器返回的路径，表达**逻辑规划**。路径选择沿用 Rust `previewPolicy` 的结果，前端负责绘制、选择和详情展示。

- 节点位置是布局信息；管理员的国家标签不等于设备经纬度。
- 图中的方向、必经节点和出口对应当前选定流量的规划。
- 测量数据接入前不生成 RTT、链路健康或实时流量动画。
- 图形视图应同时提供可读的路径列表、节点名称与地址信息。

`previewPolicy` 使用调用方提交的策略和 controller 当前节点清单求值。预览响应的 revision 不证明提交的策略仍是最新已保存策略。地图必须保留所用策略快照与版本，识别过期结果，或者重新读取后再求值；输入变化后不能继续展示旧结果为当前路径。

## Routing 的编辑流程

规则列表优先展示匹配范围、动作、经由节点和顺序，将详细条件放到聚焦的编辑区域。首次使用也应能分清三件事：

1. **谁的流量**：源节点、管理员国家标签；各列表内部 OR，维度之间 AND。
2. **什么目标**：Mesh / 互联网范围，以及任一节点、域名 suffix、CIDR 或国家条件。
3. **怎么走**：拒绝、直接路由，或按顺序经过指定节点并使用明确出口。

规则仍按 first-match 执行，默认动作可选 direct / reject。空选择表示任意时，应在规则摘要中明确展示。域名首版仅做标签边界 suffix。

### 草稿、预览与保存

- 修改规则首先形成草稿；编译预览使用草稿和显式流量上下文。
- 保存始终使用载入草稿时的基准 revision。预览观察到新版本不能悄悄推进保存基准。
- `409` 冲突及 `422` 校验失败保留草稿；只有成功保存或明确重新载入才更新基准。
- 被撤销或未知的节点引用继续可见，供用户修复；不能自动删掉规则或必经节点。
- 异步结果须与发起它的草稿、流量及上下文关联，避免较旧响应覆盖后续编辑。

规则编辑 Sheet 先修改工作副本，“应用到草稿”后才进入策略草稿；关闭未应用的修改会询问是否放弃。Sheet 打开时全局 ⌘K 不越过该编辑流程。

已应用到草稿的修改及其原始 CAS 基准保存在当前已登录界面的内存中，跨侧栏、⌘K 和浏览器前后导航可恢复；登出后清除。保留草稿期间，无论停在哪一页，整页刷新或关闭标签页都会触发浏览器离开提示。草稿不写入 localStorage 或 sessionStorage。

删除撤销只作用于创建它的草稿版本。成功保存、重新载入或放弃修改会使旧撤销操作失效。历史预览保留提交时的流量信息，后续修改输入只会标记结果过期，不会改写旧结果中的目标。

草稿比较使用固定对象字段顺序，避免 SDK 解析顺序造成“未编辑却显示已修改”；规则、经由节点和条件数组的顺序仍保留。保存后早于新基准的历史预览提示重新预览，只有观察到更高的 controller 版本才提示载入最新版本。

配置确认与策略保存分开呈现：controller 保存策略后，节点还需要拉取、校验、落盘并 ACK。“已确认保存”不代表 OS 网络或转发已经生效。

## 组件与结构

以完整 shadcn 组件集作为界面基础，业务层按需组合。导航外壳、节点、注册、路由和地图按功能组织；共享组件负责一致的视觉与交互，业务状态留在所属功能。

当前 `base-mira` registry 可用组件已补齐，本地共有 62 个 UI 组件文件，包括单独补入的 Sonner；该风格的 `form` registry 项不提供文件，表单基础由 `field` 等组件承接。业务组件分别位于 `apps/web/components/shell`、`nodes`、`routing`、`topology`、`dashboard`、`auth` 与 `enrollment`，原生 UI 基础位于 `components/ui`。

优先使用组件库的语义主题变量、Select、Sheet、Dialog、Tooltip 等能力，在应用层统一字号、间距与明暗主题。管理请求继续使用生成 SDK，页面与每个 Server Action 都执行服务端认证；管理员凭据不进入客户端状态或图表数据。

## 验证入口

- `pnpm test:web`：使用生成 schema 验证草稿比较、单条规则变化与有序数组语义。
- `pnpm test:e2e`：真实 controller / agent / Web 验证注册、撤销、匿名 Server Action 重放拒绝、规则 Sheet、Base UI 选择器、历史预览、删除撤销、跨页草稿及原始 CAS 基准保留。
- 视觉审阅使用隔离服务的真实四节点清单、配置回执与三节点规划路径，覆盖明暗主题和桌面 / 移动视口；不向当前运行网络写入演示策略。
