# 加密边界与真实追踪

**推荐主线：端到端加密 + 真实数据面 `meshway trace`。** 原生操作系统 traceroute 是后续兼容目标，不是首版交付的硬门槛。当前两者都未实现。

## 已确认的安全方向

- 优先保留端到端加密（E2E）。
- 如果 E2E 与原生 traceroute 组合代价过高，可以显式评估可信节点逐跳解密的初始方案。
- 逐跳可信路由是独立的信任选择，最终采用方式尚待决定。
- **不允许连接失败时静默丢弃 E2E，不允许自动切换信任语义。**

这意味着原生 traceroute 的困难应先通过专用 mesh trace 解耦，而不是默认牺牲 E2E。

## E2E 的端点在哪里

| 流量 | mesh 加密边界 | 谁能看到解密后的业务包 |
| --- | --- | --- |
| NYC 访问 mesh 内 SHA | NYC → SHA | 两端；LAX 只做密文中转 |
| NYC 经 SHA 访问外部网站 | NYC → SHA 出口 | 两端；SHA 需解封装后出网 |

```text
NYC ═══════ E2E 密文，经 LAX 转发 ═══════ SHA ──→ 外部网站
                                             mesh 边界之外
```

**不能承诺 mesh E2E 延伸到任意网站。** 从 SHA 到外部目标的机密性依赖应用 TLS 等协议；Meshway 不控制网站端的密钥与终止点。

E2E 不等于隐藏全部元数据。中间节点通常仍需要看到足够的外层路由信息，网络观察者也可能看到大小、时序和邻接地址。应在封装设计中明确哪些路径标识和诊断信息可见。

## 两种显式安全模式

| 模式 | 语义 | 当前结论 |
| --- | --- | --- |
| `e2e`（概念名） | 业务密文只在源与最终 mesh 终点 / 出口解开；中间节点转发密文 | 推荐主线，具体密钥协议与封装待定 |
| `trusted-routing`（概念名） | 受信任中间节点可逐跳解密、处理并重新加密 | 可评估的显式替代方案，未决定首版交付 |

概念名尚不是 API 枚举。若实现两种模式，建议把模式纳入策略、节点能力校验、诊断输出及审计。任何模式变化都需要明确配置和授权；E2E 候选不可用时应失败，不能自动尝试另一信任模式。

密钥生成、注册、轮换、吊销、节点认证及重放防护尚需协议设计。开发态 UUID 和进程报告不承担这些职责。

## `meshway trace` 必须测到实际转发

显示控制面编译出的 `NYC → LAX → SHA` 只能叫**计划路径**。真实 trace 应通过数据面实际发送探测，证明探测经过哪些邻接，并标出未响应的段。

建议诊断区分以下内容：

1. **计划**：匹配规则、授权结果、策略版本和要求的 hop。
2. **观测**：实际响应的节点身份、所用传输、探测时刻和逐段结果。
3. **差异**：超时、能力不匹配、路径约束失败或计划与观测不一致。

建议探测与业务使用相同的路径选择及转发机制，并绑定路径 / 流上下文。响应需认证、防重放与速率限制。不能用单独连通 controller 的心跳冒充业务路径验证。

中间节点可处理受限的外层探测信息，而不获得业务明文；具体探测报文和证据模型仍需实现验证。观测到的往返时间包含探测和回程成本，不能不加说明地当作每跳单向时延。

## 为什么原生 traceroute 另行推进

操作系统 traceroute 依赖 IP TTL / Hop Limit 递减及 ICMP 响应。封装隧道可能把多个 mesh hop 隐藏为一个 IP hop；代理链日志也不等于 IP 层 hop。

让系统工具呈现 mesh 中间节点，需要实现和验证：

- 内外层 TTL / Hop Limit 的语义及递减位置。
- ICMP Time Exceeded、Packet Too Big 的生成、认证边界与回程。
- 加密载荷下可返回的诊断信息，以及隐私暴露。
- IPv4 / IPv6、不同探测协议和不同操作系统行为。

这些工作不会由“启用多跳”自动完成。首版优先证明 E2E 转发与真实 mesh trace，再判断原生工具兼容的成本。
