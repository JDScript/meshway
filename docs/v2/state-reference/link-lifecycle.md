# 按需连接与保活

**建议默认：按需建立、建立后复用、无活跃依赖时延迟回收。** 历史曲线不是让所有节点常驻连接的理由。具体保活／空闲时间仍需结合实际 NAT 和负载确认。

## 生命周期

```text
没有连接
  → 产生获准业务需求
  → 发现／协调／握手
  → 复用已认证 link
  → 没有活跃业务依赖，进入空闲保留期
  → 空闲期结束后释放
```

按需不等于每个 IP 包重新握手，也不等于每个新 TCP 流必须建立一个新外层连接。多个允许的业务流可复用同一条 link。

回收不能仅看“最近有没有数据包”：仍有活跃流、半关闭会话或必要路径依赖时，要按实际会话生命周期处理。释放底层通道也不能借机给旧业务更换逻辑路径或清除授权边界。

## 三种不同的行为

| 行为 | 目的 | 默认范围建议 |
| --- | --- | --- |
| NAT keepalive | 维持仍需使用的 socket 映射 | 当前需要保留的通道，不是全网所有 peer |
| 连接健康探测 | 决定重试／故障切换等运行行为 | 连接 owner 管理的活动通道 |
| 延迟历史采样 | 保存真实测量结果供查看 | 订阅统一探测结果，不另建连接凑曲线 |

保活报文不一定是可用的 RTT 测量；没有对应的 request/reply 计时就不能生成延迟点。传输协议、映射条件不同，保活策略可以不同，但仍由平台定义，不增加设备手工配置步骤。

## 没有连接时

节点确认没有 link 时，State 表达无连接；Controller 只是没收到新报告时则是未知／过期，不能猜已经断开。历史里这段时间可以没有 RTT；没有采样不表示 RTT=0、网络离线或丢包率=100%。

下一次业务触发后，可以分别记录“重新建连耗时”和随后活动 link 的 probe 结果，不把冷启动耗时混入稳定 RTT。

若产品以后确实需要持续测量指定路径，应显式定义诊断任务及预算；不能悄悄把普通历史查看变成后台全网拨号。

用户已提出 Console 实时 watch 路径的目标，方案见 [Realtime Observation](/v2/state-reference/realtime)。这可以是临时诊断需求：仅观察期间准备／持有获准路径，到期后回到普通回收策略；不改变默认按需建连。

## 可选常驻连接

固定少量邻接、预热备用路径可以作为后续高级执行策略，但与 topology 的许可不同，仍受其约束。是否需要这个入口尚待确认，本稿不默认要求全网常驻。
