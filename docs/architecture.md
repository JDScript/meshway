# 架构与设计状态

Meshway 的目标是一个以节点身份为基础的 Rust mesh 网络：根据来源身份、位置与目标域名 / 地址选择路径，用显式的有序节点连接跨区域网络，并为每条逻辑相邻连接提供多种传输候选。

## 设计状态

| 状态 | 含义 | 本项目的关键内容 |
| --- | --- | --- |
| **已确认** | 用户明确要求的产品方向 | Rust controller + agent；类 Tailscale 的身份与 mesh；域名 exact / prefix / suffix 与 CIDR 分类；来源位置与节点身份；有序 `via` 与独立出口；每条逻辑邻接的多传输，首版采用优先级主备，健康高优先级优先并支持故障切换 |
| **已确认** | 安全与开发约束 | 优先 E2E；真实 mesh trace；原生 traceroute 不作为首版硬门槛；禁止失败时静默改变信任模型；Rust 类型及路由关联 OpenAPI 为契约来源；生成客户端；前后端交付同一 API 切片 |
| **建议默认** | 当前推荐方案，尚非冻结协议 | 有序 first-match；ACL 独立求值；低数值高传输优先级；按流固定主备选择；同一逻辑邻接内回退；E2E + mesh trace 主线 |
| **当前实现选择** | 本切片的工程选择，不表示用户逐项确认协议细节 | 单 controller SQLite；管理员 bearer；限时一次性注册令牌；Agent 持久化节点 bearer；心跳与撤销；Web 使用 HttpOnly cookie 和受保护的 server action |
| **待决策** | 需要设计评审与原型验证 | mesh 公钥身份、密钥生命周期与 E2E 握手、数据面封装、首批传输、域名前缀精确定义、DNS 接管平台顺序、默认无匹配行为、回程路径、故障后的路径替代，以及 trusted-routing 首版是否交付 |
| **已实现** | 控制面行为测试、生成漂移检查及真实服务浏览器端到端测试已通过 | 注册、持久化、凭据权限、心跳、撤销和 Web 登录闭环；尚不包含 mesh 地址、配置分发、路由策略或网络转发 |

## 控制面与数据面

```text
                         ┌────────────────────┐
                         │ Next.js 管理界面    │
                         └─────────┬──────────┘
                              生成 TS SDK
                                   │
                         ┌─────────▼──────────┐
                         │ Rust controller    │
                         │ 凭据 / 持久清单     │ ← 已实现
                         │ 策略 / 配置分发     │ ← 后续能力
                         └─────────┬──────────┘
                              生成 Rust 客户端
                                   │
       ┌───────────────────────────▼───────────────────────────┐
       │ Agent：本地 DNS → 分类 → 授权检查 → 路径 → 传输候选   │ ← 设计目标
       └───────────────────────────┬───────────────────────────┘
                                   │
                         NYC → LAX → SHA → 目标
```

当前已交付 HTTP 控制面：通过注册建立节点凭据身份，再用心跳维护联系记录。图中的策略分发、DNS、mesh 公钥认证与数据转发尚未实现；HTTP API 的 schema 和生成客户端不是网络连通性的证明。

控制面的设计职责是维护身份、节点清单、授权与策略版本，编译和分发一致的配置。Agent 执行本地解析、分类、转发、连接管理与诊断。业务流量经过指定 Agent，controller 不应被默认当作业务中继。

### 身份与观测信息分开

控制面凭据身份由管理员授权注册、服务端分配节点 ID 和节点 bearer 建立。心跳由凭据派生身份，调用方不能任选节点 ID。节点名、IP、国家或城市标签都不能单独证明身份；mesh 对等节点的公钥认证与 E2E 握手仍需后续设计。

来源国家可以是控制面观测出口地址得到的标签，也可以是经授权维护的部署属性。必须记录其来源与更新方式；代理、NAT、漫游和定位误差会影响结果。`source_country = US` 与“这个密钥被授权访问某资源”是不同判断。

### 当前持久化与部署选择

controller 的单实例 SQLite 记录节点、注册令牌消费和撤销状态，数据目录锁阻止同时启动第二个实例。Agent 的私有状态文件在网络 I/O 前保存节点凭据，支持重启和响应丢失后的身份恢复。当前文件存储使用 Unix `0700` 目录与 `0600` 文件。Web 使用 8 小时 HttpOnly / Strict cookie，仅在服务端携带管理员凭据调用生成 SDK，逐次检查读取与管理 action。`last_seen` 是最近联系记录，`node_count` 包括已撤销节点，不代表健康隧道数。

这一选择不提供高可用或多 controller 复制；远程 HTTPS 由独立部署层终止 TLS。注册恢复、权限与故障语义见[控制面注册与持久化](/enrollment)。

## 四个独立层次

1. **分类**：这条流来自谁、去哪里？域名上下文从何而来？
2. **授权**：这个身份是否允许访问目标、使用中间节点和出口？路由匹配不授予访问权。
3. **逻辑路径**：必须依次经过哪些 mesh 节点，最后由谁终止隧道或出网？
4. **传输**：相邻两个节点用哪种承载建立连接？候选必须符合能力与安全模式。

例如 `NYC → LAX → SHA` 是逻辑路径；`NYC ↔ LAX` 可以有多个传输候选。换掉这一段的承载不等于允许跳过 LAX。目标域名、DNS 上游以及控制通道的流量也不能被一个不加区分的 TUN 规则递归捕获。

## 小而清晰的 Rust 边界

初始工作区保持少量模块，待稳定边界出现后再拆分：

| 边界 | 职责 |
| --- | --- |
| `crates/protocol` | Rust 请求 / 响应类型、序列化与契约基础 |
| 生成的 Rust control client | Agent 调用 HTTP API，避免手写平行 DTO |
| `apps/controller` | API 路由、当前切片的凭据权限与 SQLite 存储；之后的策略编译和分发 |
| `apps/agent` | 当前切片的注册、本地状态与心跳；之后的节点数据面 |
| `@meshway/control-client` | 生成 TypeScript 类型、客户端与运行时响应验证 |
| `apps/web` | Next.js + shadcn，消费已交付 API |
| `docs` | 架构、设计状态与验收说明 |

WASM 是未来共享策略编译器的可选方式。仅为 HTTP 客户端共享类型不需要引入 WASM。
