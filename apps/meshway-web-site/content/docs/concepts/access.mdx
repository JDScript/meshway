---
title: 访问权限
description: 决定哪些节点可以向哪些目标发起什么流量。
---

访问权限回答的是业务问题：谁可以访问目标上的哪个服务。它由来源、目标、协议与端口组成。

例如，来源为 `group:dev`、目标为 `tag:backend`、协议与端口为 `tcp:443`，表示开发组的用户身份设备可以访问后端标签节点的 TCP 443 端口。

## 默认拒绝，规则取并集

没有匹配的允许规则时，经 Mesh 发起的新访问被拒绝。访问规则只表达允许，所有匹配规则的权限取并集，与排列顺序无关。

新网络预置一条允许网络内节点互访的规则。因此，收紧权限时要修改或删除这条宽规则；在它下面增加一条只允许 TCP 443 的规则，不会限制其他访问。空的访问规则列表不允许新的 Mesh 业务访问。

## 协议与端口怎么写

| 写法            | 允许的业务                           |
| --------------- | ------------------------------------ |
| `tcp:443`       | TCP 目的端口 443                     |
| `tcp:8000-8100` | TCP 目的端口 8000 到 8100            |
| `udp:*`         | UDP 任意目的端口                     |
| `icmp:*`        | ICMP，包括 `meshway ping` 所需的授权 |
| `*`             | 模型支持的全部业务协议与端口         |

业务协议与节点之间的承载独立。允许 TCP 443 业务并不要求节点使用 Native TCP 承载；这部分由[组网规则](/docs/concepts/topology)和节点传输配置决定。

## 单向与双向

默认由来源主动发起，已建立会话的回复可以返回。**双向**允许目标也反向发起新的同类会话。

如果 A 只需访问 B 的 Web 服务，A 到 B 的单向规则足够。只有 B 也需要主动访问 A 的对应服务时，才需要双向或另一条访问规则。

## 授权之后还需要什么

通信还需要可用的节点、监听与拨号器，以及符合组网规则和流量路由的实际路径。中转不会把原来源身份变成中转节点的身份，也不会自动授予访问中转节点服务的权限。

使用[路径检测](/docs/console/diagnostics)查看匹配的访问规则，再用实际探测检查连通性。完整配置结构见 [API：读取配置](/docs/api/configuration/get-configuration)。
